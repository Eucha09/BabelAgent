# 에이전트 프롬프트와 배치

## 세션 수명

| 작업 | 세션 | 재사용 |
|---|---|---|
| 배치 번역 | 배치마다 새 `query()` | × |
| 컨텍스트 추정 | 배치마다 새 `query()` | × |
| 용어 추출 | 배치마다 새 `query()` | × |
| 용어 번역 | 배치마다 새 `query()` | × |
| 행 단위 리롤 | 일회성 `query()` | × |
| 에이전트 패널 채팅 | `resume` 유지 | ○ |

배치 세션을 재사용하지 않는 이유: 앞 배치의 결정이 뒤 배치에 암묵적으로 번지면 결과를 재현할 수 없고, 실패한 배치만 다시 돌릴 수도 없다.

## 공통 옵션

```ts
query({
  prompt: batchPrompt,                  // 가변 부분
  options: {
    settingSources: [],                 // 사용자 PC 설정과 이 저장소의 CLAUDE.md 차단
    cwd: projectDir,
    tools: [],                          // 내장 도구 전부 끔
    disallowedTools: ['Bash', 'Write', 'Edit', 'NotebookEdit'],
    permissionMode: 'dontAsk',         // 허용 목록에 없으면 묻지 않고 거부
    systemPrompt: fixedPrompt,          // 고정 부분. 작업마다 한 번 만들어 모든 배치가 같은 문자열을 쓴다
    mcpServers: { babel: submitServer },// 배치 전용 서버(아래). 배치마다 새로 만든다
    allowedTools: ['mcp__babel__submit_translations'],
    maxTurns: 6,                        // 제출 + 수정 한 번 + 여유
    model,                              // translate.model. default 면 넣지 않아 CLI 설정을 따른다
    effort,                             // translate.effort(사고 수준). 모델이 지원하지 않는 수준은 CLI 가 낮춘다
    pathToClaudeCodeExecutable: appSettings.cliPath ?? undefined,
  },
})
```

- 배치 세션의 도구는 그 작업의 제출 도구 하나다 — 번역 `submit_translations`, 컨텍스트 추정 `submit_context`, 용어 추출 `submit_terms`, 용어 번역 `submit_term_translations`. 필요한 데이터는 프롬프트에 다 들어 있으므로 읽기 도구를 주지 않는다.
- 컨텍스트 추정·용어 추출·용어 번역도 `translate.model`·`translate.effort`를 따른다. 작업은 종류와 상관없이 한 번에 하나만 돈다(같은 사용량 한도).
- MCP 도구 이름은 `mcp__<서버>__<도구>` 로 허용 목록에 넣는다(서버 이름 `babel`).

## 프롬프트 조립 순서

고정 부분 → 가변 부분. 고정 부분은 프로젝트 설정이 바뀌지 않는 한 **문자 단위로 동일**해야 한다(프롬프트 캐싱).

1. 역할과 출력 규약 — 상수 문자열. `note`를 쓸 언어(`sourceLanguage`)도 여기서 지시한다
2. 게임 소개 (`game.intro`)
3. 톤 가이드 (`game.toneGuide`)
4. 스타일 규칙 (`styleRules`, `id` 순 정렬)
5. 언어 지시 — `sourceLanguage` → 대상 언어
6. ── 여기까지 고정 ──
7. 이번 배치에 등장하는 용어집 항목만 — 승인된 용어를 QA 의 용어 탐지(`findTermsInSource`)와 같은 방식으로 문자열마다 찾아 합친다. 배치를 시작할 때 넣은 용어를 작업 로그에 남긴다(`배치 3 시작 (30행) · 용어 4개: …`, 상세에 확정 번역과 strict)
8. 이번 배치 문자열(키, 원문, context, ui_type, max_len, vars)

금지:

- 고정 부분에 타임스탬프, 배치 번호, 진행률, 난수를 넣지 않는다.
- `styleRules`를 삽입 순서대로 넣지 않는다. 정렬해서 넣어야 추가·삭제 시 앞부분이 유지된다.
- 전체 용어집을 매번 넣지 않는다. 배치 문자열에 등장하는 항목만 필터링한다(`filterTermsForTexts`, 패널의 `get_glossary_terms`도 같은 함수).

## 배치 산정

```
배치에 행을 하나씩 담다가 다음 중 먼저 걸리는 쪽에서 끊는다
  · 행 수 >= batch.maxRows        (기본 30)
  · 원문 누적 문자 수 >= batch.maxSourceChars  (기본 3000)
단, 한 행이 혼자 maxSourceChars를 넘으면 그 행만으로 배치를 만든다
```

- 정렬은 key 순. 같은 화면/태그의 문자열이 같은 배치에 모이면 문맥이 좋아지므로, `tags` 기준 그룹 정렬은 후순위 개선 과제로 둔다.
- 동시 실행은 `batch.concurrency`(기본 2, 상한 3). 코드에서 `Math.min(value, 3)`으로 잘라낸다.

## 응답 규약

에이전트는 텍스트로 답하지 않고 `submit_translations` 도구로 제출한다. 도구 입력 스키마가 곧 검증 스키마다(`src/core/translate/submission.ts`).

```ts
const SubmittedTranslation = z.object({
  key: z.string().min(1),
  text: z.string(),
  confidence: z.number().min(0).max(1),
  note: z.string().optional(),
})
// 도구 입력: { translations: SubmittedTranslation[] }
```

검증 순서:

1. 입력 스키마(zod) — SDK가 도구를 부르기 전에 검사한다. 어긋나면 에이전트에게 오류가 돌아간다
2. 키 집합(누락·초과·중복)과 빈 번역 — 도구 핸들러가 검사한다. 실패하면 문제를 돌려주고, **같은 세션에서 한 번만** 다시 받는다
3. 행별 QA(`docs/qa-rules.md`) — 첫 제출에서는 오류를 모두 돌려줘 고칠 기회를 준다. 마지막 제출에서 구조 오류(변수·중괄호·태그)가 남으면 배치를 거부하고, 길이 초과·strict 용어 위반만 남으면 받아서 기록한다(검토 화면이 오류로 띄운다). 판정은 `judgeSubmission`(`src/core/translate/submission.ts`)
4. 통과 → 보관해 두었다가 세션이 끝나면 배치 전체를 원자적으로 기록, 상태 `draft`. 번역할 때 본 원문을 `source_snapshot`에 함께 남긴다

- 도구 응답의 문제 목록은 `키: ruleId (대상)` 형식의 짧은 영어다. 예: `quest_01: var.missing (playerName); title: len.over_max (23/20)`.

- 제출이 두 번 다 실패하거나 제출이 없으면 배치 실패로 보고한다. 배치 단위 자동 재시도는 하지 않는다.
- 통과한 제출이 있으면, 그 뒤 한도 대기로 중단 신호가 왔더라도 기록한다. 배치가 온전하므로 버릴 이유가 없다.
- 기록은 번역 파일을 다시 읽어 합친 뒤 원자적으로 쓴다. 동기 함수 하나라서 같은 프로세스의 다른 작업자가 사이에 끼지 못한다. `approved` 는 여기서도 한 번 더 막는다.

## 작업별 프롬프트

### 번역

- 출력: `TranslationResponse`
- 지시 요점: 변수와 태그를 원문과 동일한 집합으로 유지, `max_len` 준수, 용어집의 확정 번역 사용, 불확실하면 `confidence`를 낮추고 `note`에 이유.
- `max_len`은 화면 길이로 센다고 QA 와 같은 기준을 함께 알린다(`DISPLAY_LENGTH_RULE`): 리치 텍스트 태그는 세지 않고, 변수는 `vars`의 example 로(없으면 적힌 그대로), 분기가 있는 포매터는 가장 긴 분기로 센다. 이 문장이 없으면 에이전트가 태그까지 세어 태그가 많은 문장을 필요 이상으로 줄일 수 있다(2026-11-06).
- `note`는 원문 언어(`sourceLanguage`)로 쓴다. 메모를 읽는 검토자는 원문을 쓰는 사람이기 때문이다. 지시문 자체는 영어로 두고 언어 이름만 설정에서 넣는다 — 특정 언어를 하드코딩하지 않는다. 고정 부분이라 프로젝트의 원문 언어가 같으면 문자열이 바뀌지 않는다(캐싱 유지). 행 재번역도 같은 고정 부분을 쓰므로 후보 메모도 원문 언어로 나온다.
- `approved` 행은 애초에 배치에 넣지 않는다.

### 컨텍스트 추정

- 대상: 고른 필드(`context`, `ui_type`, `max_len`, `vars`) 중 원문에서 빈 칸이 있는 행. 승인을 기다리는 제안이 있는 행은 뺀다. 변수가 없는 원문에는 vars 를 묻지 않는다(`src/core/context/targets.ts`).
- 고정 부분(`buildContextSystemPrompt`): 역할, 필드 설명, 규칙, 출력 규약, 게임 소개. 사람이 읽을 글(context, 변수 meaning, note)은 원문 언어로 쓰게 한다. `max_len`은 버튼·탭처럼 길이 제한이 분명할 때만 내라고 하고, 원문이 아니라 **모든 대상 언어 번역문**의 한도이니 가장 긴 번역에 여유를 더해 넉넉하게 잡으라고 지시한다(대상 언어 목록을 함께 준다). 길이를 세는 기준은 번역과 같은 `DISPLAY_LENGTH_RULE`이다.
- `max_len` 하한(코드): 받은 값이 원문 표시 길이 × `context.maxLenRatio`(기본 2.5, 최소 10자)보다 작으면 그 값으로 올린다(`generousMaxLen`). 원문 길이는 QA 와 같이 센다 — 태그는 빼고 변수는 제안된 example(없으면 기존 vars 의 example)로 바꾼다. 에이전트가 원문(한국어) 길이에 맞춰 빡빡하게 잡는 일이 실측에서 나와 넣었다(2026-10-22, 사용자 요청).
- 가변 부분(`buildContextBatchPrompt`): 프로젝트에서 이미 쓰는 ui_type 목록(표기를 맞추게), 행마다 키·원문·이미 있는 메타데이터·`fill`(채울 필드)·`variables`(코드가 원문에서 뽑은 변수 이름).
- 출력: `submit_context` 도구 `{ entries: { key, context?, ui_type?, max_len?, vars?: { name, type?, meaning, example? }[], confidence, note? }[] }` (`src/core/context/submission.ts`).
- 판정: 키 집합(빠짐·남음·겹침), 요청한 context·ui_type 이 비지 않았는지, vars 이름 집합이 `variables`와 같은지(`caseSensitive` 따름). 첫 제출의 문제는 돌려줘 한 번 고치게 하고, 마지막 제출은 문제없는 행만 받는다 — 버린 행은 다시 실행하면 그 행만 돈다. 받을 행이 하나도 없으면 배치 실패.
- 결과는 원문에 바로 쓰지 않고 `context_suggestions.csv`에 제안으로 쌓는다. 요청한 필드만 담는다. 사람이 컨텍스트 화면에서 고치고 승인해야 원문에 들어간다. 신뢰도가 `review.lowConfidence` 미만인 제안은 구분 표시하고 "기준 이상 선택"에서 뺀다. 번역 상태에는 영향을 주지 않는다.
- 실측(2026-10-22, haiku · 낮음): 10행 · 배치 3개 · 작업자 2 → 약 21초. 이미 채워진 칸(dialog 행의 context·ui_type)은 제안하지 않고 vars 만 냈다. 신뢰도 0.6 인 아이템 이름 1행이 "신뢰도 낮음"으로 남았다.

### 용어 추출

- 대상: 전체 원문 또는 선택 행. 번역과 같은 배치 산정.
- 고정 부분(`buildTermsSystemPrompt`): 역할, 무엇을 뽑을지(고유명사·게임 용어·반복 UI 용어), 후보마다 낼 것, 출력 규약, 게임 소개. **후보만 찾고 번역하지 않는다** — 번역은 용어 번역 작업이 빈 칸을 채운다(사용자 결정, 2026-11-02. 그 전에는 추출하면서 대상 언어별 번역 제안도 받아, 대상 언어를 늘리면 다시 추출하거나 한 용어씩 재번역해야 했다). 대상 언어도 넣지 않아 언어를 바꿔도 캐시가 남는다. note·reason 은 원문 언어로.
- 가변 부분(`buildTermsBatchPrompt`): 이 배치 원문에 이미 나오는 용어집 용어(승인 대기 포함, "Already in glossary"), 행마다 키·원문·context. 용어집은 배치마다 다시 읽는다.
- 출력: `submit_terms` 도구 `{ terms: { term, pos?, note?, reason?, confidence }[] }` (`ExtractedTerm`, `src/core/terms/submission.ts`). 번역을 보내도 스키마가 버린다. 빈 목록도 받는다. 패널의 `propose_glossary_terms`는 사용자가 번역을 말할 수 있어 번역을 선택으로 받는다.
- 판정: 용어가 그 배치 원문에 실제로 나오는지(QA 의 용어 탐지와 같은 방식 — context 에만 있는 낱말은 안 된다), 자리표시자·태그가 섞였는지, 같은 제출 안의 겹침, 대상 언어 코드. 이미 있는 용어는 문제로 보지 않고 조용히 뺀다. 첫 제출의 문제는 돌려주고 마지막 제출은 문제없는 후보만 받는다.
- 결과는 `glossary.csv`에 번역 칸이 빈 채로 `status: pending`으로 들어간다(기록할 때 다시 읽어 이미 있는 용어는 빼므로 병렬 배치가 같은 용어를 내도 한 번만 들어간다). 사용자가 승인해야 `approved`가 되고, 승인된 항목만 번역 프롬프트와 QA 에 쓰인다.
- 실측(2026-11-02, haiku · 낮음, 8행 샘플): 1배치 · 후보 5개(마나 물약·화염구·마나·골드·수호자), 번역 칸은 모두 빔.
- 실측(2026-10-22, haiku · 낮음): 10행 · 배치 3개 → 약 24초, 후보 6개(골드·체력 물약·설정·구매·제단·저장). 두 배치가 context 에만 있던 낱말("수호자", "인벤토리")을 냈다가 "not found in the source strings"로 돌려받고 고쳐 냈다.

### 용어 번역(용어집 화면)

- 대상: 고른 언어의 **빈 번역 칸**. "빈 칸 전체" 또는 그리드에서 고른 용어. 승인 대기 용어와 승인된 용어를 모두 본다. 이미 있는 번역은 덮지 않는다 — 덮어쓰기는 [선택 재번역]. 화면은 언어마다 빈 칸 수를 보이고, 언어를 따로 고르지 않으면 빈 칸이 있는 언어를 모두 고른 것으로 본다.
- 배치: 용어 20개(`TERMS_PER_BATCH`), 용어집 순서. 배치를 돌릴 때 용어집을 다시 읽어 그 사이 채워진 언어·지워진 용어는 뺀다(`src/main/jobs/term-translate-job.ts`).
- 고정 부분(`buildTermTranslateSystemPrompt`, `src/core/terms/translation.ts`): 역할, 용어마다 translate_to 의 언어로 옮길 것, 예문으로 뜻을 잡고 예문의 기존 번역(특히 승인된 것)이 일관되면 따를 것, 다른 언어의 용어집 번역과 같은 뜻·같은 방식(음역/번역)을 지킬 것, 사용 지침을 따를 것, 문장이 아니라 용어만, reason(선택)은 원문 언어, 출력 규약, 게임 소개·톤 가이드·스타일 규칙(id 순, 문장 번역과 같은 `styleRulesSection`). 규칙 목록은 문장 번역과 같아서 반말·존댓말처럼 문장에만 맞는 규칙도 섞여 있으므로, 대문자 표기·음역·문자 체계처럼 **용어 표기에 해당하는 규칙만** 따르라고 한다(`TERM_STYLE_LINE`, 사용자 요청 2026-11-02). 대상 언어는 넣지 않는다(캐시).
- 가변 부분(`buildTermTranslateBatchPrompt`): 이번 배치에서 쓰는 언어(코드와 이름), 용어마다 term·pos·note·translate_to(채울 언어)·known_translations(다른 언어의 용어집 번역)·예문. 예문은 [용어 추가]와 같은 방식(`pickTermExamples`)으로 용어마다 3행(`EXAMPLES_PER_TERM`), 원문에 없으면 그 사실을 밝힌다.
- 출력: `submit_term_translations` 도구 `{ terms: { term, translations: { language, text }[], reason?, confidence }[] }`. 판정(`judgeTermTranslations`): 배치 용어를 빠짐없이 한 번씩(대소문자 무시), 채울 언어마다 빈 번역이 아닐 것. 채울 언어가 아닌 번역은 조용히 버린다. 첫 제출의 문제는 돌려주고, 마지막 제출은 문제없는 용어만 받는다(하나도 없으면 거부). 버린 용어는 칸이 빈 채로 남아 다시 돌리면 그 칸만 채운다.
- 기록(`fillTermTranslations`): 다시 읽기 → **아직 빈 칸만** 채우기 → 원자적 쓰기. 그 사이 사람이 채운 칸은 덮지 않는다. 승인된 용어에 채운 언어는 `pending_languages`에 넣는다 — 그 언어의 번역은 [선택 승인] 전까지 번역 프롬프트와 QA 에 쓰이지 않고, 다른 언어의 확정 번역은 계속 쓰인다(사용자 결정, 2026-11-02). 승인 대기 용어는 용어 전체 승인으로 함께 확정되므로 표시하지 않는다.
- 작업 로그에 채운 용어·언어별 번역·reason 을 남긴다.
- 번역 작업은 시작할 때 그 범위에 나오는 승인된 용어 중 그 언어의 확정 번역이 없는 용어(빈 칸이거나 승인 대기)를 경고로 알린다 — 대상 언어를 늘린 뒤 용어집을 채우기 전에 번역부터 돌리는 경우.
- 실측(2026-11-02, haiku · 낮음, 같은 샘플에 대상 언어 ja 를 더한 뒤): 용어 7개 · 칸 12개 · 1배치 약 9초. 승인된 "바벨탑"(en 있음)은 ja バベルの塔 만 채워지고 `pending_languages: ja`, 후보 5개는 en·ja 모두 채워짐. 바벨탑만 [선택 승인] → 대기 언어 해제. 이어서 ja 번역 작업을 시작하자 "체력 물약"(ja 대기)이 경고에 나오고 바벨탑은 バベルの塔 로 프롬프트에 들어갔다.

### 용어 추가(용어집 화면)

- 사용자가 용어 하나와 (선택) 품사·분류·사용 지침·strict 를 넣는다. 이미 있는 용어, 원문에 없는 용어는 세션을 열기 전에 거부한다(대화상자도 입력하는 동안 찾은 행 수와 함께 막는다).
- 예문(코드, `src/core/terms/addition.ts`): 원문에서 그 용어가 나오는 행을 QA 와 같은 탐지로 찾고, 최대 8행을 고른다. 기존 번역이 있는 행, 그중 승인된 행을 앞에 둔다. 행마다 키·원문·context·언어별 기존 번역과 상태를 준다.
- 고정 부분(`buildTermEntrySystemPrompt`): 대상 언어별 번역을 내되 예문의 기존 번역(특히 승인된 것)이 일관되게 옮긴 표현이 있으면 따르고, 엇갈리면 고른 이유를 reason 에. 사용자가 준 품사·지침은 그대로 두고 빈 칸만 채운다. note·reason 은 원문 언어. 게임 소개·톤 가이드·스타일 규칙(용어 번역과 같이 용어 표기에 해당하는 규칙만 따른다 — 사용자 요청, 2026-11-02). [선택 재번역]도 같은 고정 부분을 쓴다.
- 가변 부분(`buildTermEntryPrompt`): 용어, 사용자가 준 값(빈 칸은 "fill it in"), 예문(찾은 행 수 중 몇 행인지).
- 출력: `submit_glossary_entry` 도구 `{ entry: { term, pos?, translations: { language, text }[], note?, reason?, confidence } }`. 같은 용어(대소문자 무시)이고 대상 언어마다 번역이 있어야 받는다. 첫 제출의 문제는 돌려주고 마지막에도 남으면 실패.
- 기록: 사용자가 준 품사·지침·strict 를 덮어 `pending`으로 붙인다. 바로 승인하지 않는다 — 그리드에서 확인하고 [선택 승인](사용자 결정, 2026-10-26). 화면은 그 행으로 스크롤해 골라 둔다.
- 코드가 그 번역으로 확정하면 용어집 위반이 될 기존 번역 행을 언어별로 세어(QA 의 `usesTranslation`) 메시지로 알린다.
- 일회성 세션, `translate.model`·`effort`, 한도에 걸려도 자동 재시도 없음, 취소 가능. 시작·결과·실패는 작업 로그에 남는다.
- 실측(2026-10-26, 같은 샘플 복사본): "구매"(품사 "단위"만 입력) → 11초. 승인된 예문 `Buy Health Potion`을 따라 en "Buy", ja "購入", 지침은 에이전트가 채우고 품사 "단위"는 그대로, pending 으로 추가.

### 용어 재번역(용어집 화면)

- 그리드에서 용어 하나를 고르고 [선택 재번역]. 지시는 선택이고 사용자가 쓴 그대로 넣는다(비우면 "더 나은 대안").
- 용어 추가와 같은 고정 부분·예문·도구(`submit_glossary_entry`)를 쓴다. 가변 부분에 지금 번역·지침(화면이 보고 있는 값, 고친 칸 포함)과 검토자 지시를 더한다(`buildTermEntryPrompt`의 `revision`). 품사는 "사용자가 준 값"으로 넘겨 바꾸지 않고, 지침은 "다시 쓸 것"으로 표시해 **번역과 지침**을 다시 받는다 — 아직 맞는 안내는 살리고 옛 번역을 가리키는 부분은 고치거나 빼며, 필요 없으면 비운다(사용자 요청, 2026-10-26).
- 원문에 아직 없는 용어도 다시 번역할 수 있다(예문 없이, 프롬프트가 그 사실을 밝힌다). 용어 추가와 달리 막지 않는 이유: 이미 용어집에 들어 있는 용어다.
- 결과는 파일에 쓰지 않는다. 화면이 그 행의 번역 칸·근거·신뢰도에 미저장 편집으로 채우고, 사람이 [저장]해야 반영된다([변경 취소]로 되돌림). 바뀐 번역과 기존 번역과 어긋나는 행 수를 메시지로 알린다. 상태(승인/대기)는 바꾸지 않는다.
- 처음에는 번역만 다시 받았는데, 지침이 옛 번역을 언급하면(예: "Purchase 대신 Buy") 새 번역과 어긋나서 지침도 함께 다시 받게 바꿨다. 화면은 새 지침도 그 행의 칸에 미저장 편집으로 채우고, 메시지에 "지침 다시 씀"/"지침 비움"을 알린다.
- 실측(2026-10-26, 샘플 복사본): "구매" + 지시 "영어는 Buy 대신 Purchase 로" → 14초, en Buy → Purchase, ja 購入 유지, 승인된 예문 `Buy Health Potion`과 어긋나는 en 1행을 알림. 지침을 함께 받게 한 뒤 "영어는 Purchase 로 유지" → 12초, 지침의 "Purchase 대신 Buy" 가 "영어는 Purchase 로 통일"로 바뀌고 일본어 안내와 품사는 그대로.

### 행 단위 리롤

- 해당 행 하나 + 고정 부분 + 사용자가 입력한 추가 지시로 일회성 세션을 돌린다.
- 결과는 기존 번역을 대체하지 않고 후보로 제시한다. 적용은 사용자가 결정한다.
- 시스템 프롬프트는 배치와 **같은 문자열**(`buildSystemPrompt`)이다. 캐시가 그대로 걸린다.
- 가변 부분(`buildRerollPrompt`): 배치 프롬프트 형식의 행 하나 + 현재 번역 + (원문이 바뀐 행이면) 그 번역이 보고 쓴 원문 + 검토자 지시(비었으면 "더 나은 대안을 내라"). 지시는 사용자가 쓴 그대로 넣는다.
- 제출은 같은 `submit_translations` 도구(기대 키 하나)로 받는다. QA 오류는 한 번 고칠 기회를 주고, 그래도 남으면 후보로 받아 진단과 함께 보여 준다.
- 모델은 `translate.model`을 따른다.
- 한도에 걸리면 재설정 시각을 알리고 끝낸다. 자동으로 다시 시도하지 않는다 — 사용자가 다시 누른다.
- 시작·후보·실패는 작업 로그(`job:log`)에 남는다.

## 사용량 한도 처리

감지 경로(구조화된 신호를 먼저 본다): `rate_limit_event` 의 `status: rejected`(재설정 시각 포함) → `assistant.error === 'rate_limit'` → 결과 메시지 `errors` 와 던져진 예외의 문장. `resetsAt` 은 단위가 문서에 없어 초·밀리초를 모두 받는다.

- 한도 오류를 받으면 작업 상태를 `waiting-limit`으로 바꾸고, 진행 중인 다른 배치까지 중단 신호를 보내 큐 앞으로 되돌린다. 중단된 배치는 기록하지 않는다.
- 일시정지 중에 한도에 걸렸다면 대기가 끝나도 일시정지로 돌아간다.
- 화면 확인용: `BABEL_FAKE_LIMIT=1` 로 앱을 띄우면 실행당 한 번, 첫 배치가 20초짜리 가짜 한도 오류를 낸다.
- 응답에 재설정 시각이 있으면 그 시각까지 대기한다. 없으면 1 → 2 → 5 → 10분 백오프.
- 10분 백오프 이후에도 실패하면 자동 재시도를 멈추고 사용자 조작을 기다린다.
- UI는 남은 대기 시간과 "지금 재시도" 버튼을 보여준다.
- 대기 중에도 이미 기록된 결과는 그대로 유지된다. 재개는 미완료 행 재계산으로 이뤄진다.

## 에이전트 패널

- 유일하게 `resume`으로 이어지는 세션. 사용자가 프로젝트를 닫으면 세션 ID를 버린다.
- 사용자가 "앞으로 ~하게 해줘"라고 지시하면 에이전트는 `update_project_rules`(추가·수정·삭제 하나)를 호출한다. 도구는 저장하지 않는다 — 지금 규칙에 적용해 보고 문제가 없으면 패널 입력창 위에 확인 카드를 띄운다. 사용자가 [저장]을 눌러야 `project:rules:apply`로 `styleRules`에 들어간다(사용자 결정, 2026-10-22). 저장되지 않은 지시는 다음 배치에 반영되지 않는다 — 시스템 프롬프트가 에이전트에게 그 사실을 사용자에게 알리게 한다.
- 규칙을 고치거나 지울 때 에이전트는 `get_project_context`로 규칙 id 를 먼저 본다. 충돌하는 규칙을 새로 더하지 말고 기존 규칙을 고치라고 지시한다.
- 패널 세션의 도구: 읽기 `get_project_context`(규칙 id 포함), `get_strings_batch`, `get_glossary_terms`, 쓰기 요청 `update_project_rules`, `propose_glossary_terms`(대상 언어별 번역 포함, pending 으로 붙음). 부를 때마다 패널에 도구 줄이 남는다.
- 실측(2026-10-22): "앞으로 NPC 대사는 반말로 번역해 줘" → `get_project_context` → `update_project_rules`(add) → 카드 [저장] → r2 저장, 약 11초. "영어 부분은 빼 줘" → 같은 r2 를 고치는 update 카드. "수호자를 용어집 후보로" → `propose_glossary_terms` 1개(Guardian / 守護者) pending.
